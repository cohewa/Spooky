# Проверка и публикация Spooky

## Текущий статус

Репозиторий [`cohewa/Spooky`](https://github.com/cohewa/Spooky) **публичный**. [Spooky 0.5.24](https://github.com/cohewa/Spooky/releases/tag/v0.5.24) — первый скачиваемый релиз приложения: универсальная сборка для Intel и Apple Silicon с минимальной macOS 13, подписанная Developer ID и нотарифицированная Apple. Из 11 старых релизов Halloween Decor 2026-10-14 удалены все 22 загруженных ZIP-архива приложения и временного Safari-расширения. Их страницы и теги сохранены; автоматически создаваемые GitHub архивы исходного кода остаются доступными и не являются установщиком Spooky. Архив прежней версии `v0.4.2` был ad-hoc подписан, а проверка Gatekeeper на этом Mac вернула `rejected`. Spooky 0.5.23 опубликована как исходная версия без установочного ZIP. Safari-расширение по-прежнему устанавливается временно в режиме разработки и не входит в приложение.

## 1. Проверка перед релизом

Запустить техническую проверку:

```sh
./scripts/check-release-technical.sh
```

Скрипт проверяет синтаксис Swift/JavaScript/Python, структуру manifest и Info.plist, собирает приложение, проверяет подпись разработки и все пять видео. Это **не заменяет** ручную проверку поведения macOS.

В отдельной учётной записи macOS или чистой виртуальной машине проверить каждый эффект по отдельности и вместе:

1. Включить и выключить паутину на экране с вырезом и без него, с несколькими дисплеями и полноэкранным окном.
2. Переместить несколько стикеров, закрыть и открыть приложение, проверить сохранение позиций и выключение стикеров.
3. Проверить папку со стандартной и собственной иконкой. После выключения эффекта обе иконки должны вернуться. Если копию собственной иконки сохранить нельзя, папка не должна измениться.
4. Проверить обычные, пользовательские и динамические обои, несколько мониторов, перезапуск приложения и возврат прежних обоев. Проверить виджеты разного размера.
5. Проверить конфету в Finder, Safari, поле ввода, полноэкранном приложении и после переключения между приложениями. Выключение эффекта должно вернуть системный курсор.
6. Проверить Safari с разрешением для всех сайтов, без него и после перезапуска Safari. Временная версия расширения может исчезнуть после перезапуска; этот сценарий не считать пользовательским релизом.
7. Проверить, что в README, скриншотах и видео нет личных файлов, имён, адресов, уведомлений и токенов.

Не удалять `~/Library/Application Support/Halloween Decor/`, пока папки и обои не восстановлены.

## 2. Права на графику

52 отдельных стикера, обои, иконки папок и значок приложения созданы заново; паутина и летучая мышь лоадера нарисованы кодом. По просьбе пользователя прежняя конфетка возвращена в курсор macOS и Safari. Владелица проекта подтвердила право распространять именно эту картинку и выбрала MIT для всей графики Spooky. Шрифт Anonymous Pro сохраняет собственную лицензию SIL OFL. Исходные файлы новой графики и описание промптов сохранены в [art/GENERATED_ASSETS.md](../art/GENERATED_ASSETS.md). Факт генерации сам по себе не является юридической гарантией.

Если изображение уже попало в историю публичного репозитория, удаление только из текущего коммита не удаляет его из прошлых коммитов. Проверить историю отдельно; при необходимости согласовать очистку истории. Для настоящих секретов сначала отозвать и заменить ключи. [GitHub: removing sensitive data](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).

## 3. Подпись и распространение

Для скачиваемого приложения вне Mac App Store нужны подпись **Developer ID**, hardened runtime и notarization. Финальный архив 0.5.24 проверен локально через Gatekeeper после распаковки; дополнительная проверка установки на втором Mac остаётся полезной. `scripts/build-app.sh` делает только ad-hoc подпись. Не выкладывать её как обычный пользовательский релиз и не просить людей отключать защиту macOS. [Apple: Developer ID](https://developer.apple.com/developer-id/) · [Apple: распространение macOS](https://developer.apple.com/macos/distribution/) · [Apple: упаковка приложения](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

Safari Web Extension нужно упаковать в содержащее приложение, подписать и распространять по правилам Apple. Временная папка `safari-extension/` годится для разработки. [Apple: распространение Safari Web Extension](https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension).

`scripts/package-release.sh` собирает приложение, подписывает его с hardened runtime, отправляет архив на notarization, прикрепляет ticket, проверяет Gatekeeper и создаёт архив с SHA-256. Скрипт принимает идентификатор подписи через `SPOOKY_DEVELOPER_ID`, профиль нотарификации через `SPOOKY_NOTARY_PROFILE` и, при использовании отдельной ключницы, её путь через `SPOOKY_SIGNING_KEYCHAIN`. Секреты в репозиторий не записываются. Для постоянного Safari-расширения нужно создать содержащее приложение в Xcode; текущий скрипт его не упаковывает.

Выпуск на GitHub оформить как Release с тегом, описанием версии, архивом приложения, checksum и ссылками на видео. Текст есть в [GITHUB_COPY.md](GITHUB_COPY.md). [GitHub: releases](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository). После первого распространения дополнительно проверить установку на втором Mac, а не только в рабочей копии.

## 4. Безопасность репозитория

- Проверить `git status`, `git diff --check`, список добавляемых файлов и всю историю на секреты и личные данные до `git push`.
- Не добавлять `.env`, сертификаты, профили подписи, ключи, локальные резервные копии обоев и экспортированные системные ассеты.
- Включить secret scanning и push protection в настройках GitHub, если они доступны для репозитория. [GitHub: push protection](https://docs.github.com/en/code-security/concepts/secret-security/command-line-push-protection).
- Все 22 загруженных ZIP-архива из 11 старых релизов удалены, а в описания добавлено предупреждение. Локальная резервная копия с проверенными SHA-256 хранится в игнорируемом Git каталоге `dist/legacy-release-backup/`. Исторические теги и автоматические архивы исходного кода GitHub остаются доступны.
- Не создавать релиз с установочным архивом, пока подпись и установочный сценарий не проверены. Публичная исходная версия может быть опубликована отдельно и должна явно сообщать, что архивы исходников не являются установщиком.
